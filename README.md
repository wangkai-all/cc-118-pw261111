# 库存台账 · 应用层事务日志 + 时点恢复演示

一个自包含的 Flask + SQLite 演示应用：库存台账的入库 / 出库 / 调拨都会产生带序号的
业务事务；备份恢复页可以生成一致备份，并基于"备份快照 + 操作日志重放"把数据恢复到
备份之后的任意一笔事务，核对无误后再切换。

## 运行

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python run.py          # 默认 http://127.0.0.1:8000
```

- 台账页：`http://127.0.0.1:8000/`
- 备份恢复页：`http://127.0.0.1:8000/backup`
- 数据目录默认 `./data`（可用环境变量 `LEDGER_DATA` 覆盖），`PORT`/`HOST` 可改监听地址。

## 测试

```bash
.venv/bin/python -m pytest tests/ -q
```

## 设计要点（与需求对应）

| 需求 | 实现 |
| --- | --- |
| 业务变更与操作日志同一事务 | `app/core.py: execute_op` —— 库存变更与 `op_log` 插入在同一个 SQLite 事务中提交 |
| 日志记录完整输入、顺序、校验值 | `op_log(seq, op_type, payload, prev_checksum, checksum)`，链式 SHA-256 |
| 备份关联明确的最后事务序号 | `app/backup.py` —— 写锁内用 SQLite 在线备份接口生成一致快照，记录 `last_seq` 与链头校验值 |
| 只重放备份之后且不超过目标的事务 | `app/restore.py: start_restore` —— 重放区间为 `(backup.last_seq, target_seq]` |
| 同一笔不能应用两次 | `app/core.py: replay_one` —— 序号必须恰好接上，已存在的序号拒绝重放（另有主键约束兜底） |
| 调拨两边同时生效 | 调出扣减与调入增加在同一事务；重放每条日志也是独立事务 |
| 断号 / 损坏 / 超范围停止并指出缺口 | 重放前逐条校验序号连续性与校验值，目标超出当前最大序号直接拒绝 |
| 恢复先在独立库进行 | 恢复写入 `data/staging/` 下的暂存库，失败不影响当前库 |
| 核对后由页面确认切换 | 备份页展示暂存库与当前台账逐项对照，确认后才用暂存库整体替换当前库 |
| 重开程序后记录可查 | 备份 / 恢复记录存放在独立的 `data/meta.db` |
| 应用层事务日志 | 不解析数据库内部 WAL；恢复基线是备份时刻的快照，不是复制当前库文件 |

## 演示流程（页面上均可点击）

1. 台账页点「连续操作 ×10」产生一批事务；
2. 备份恢复页点「立即备份」，记下备份对应的最后事务序号；
3. 再做一些操作，选择备份和目标序号，点「开始恢复」——在独立暂存库中重放；
4. 核对「与当前台账对照」和「切换后将被移除的线上事务」，点「确认切换」或「放弃」；
5. 故障注入：「注入日志断号」/「注入日志损坏」后再发起覆盖缺口区间的恢复，
   观察恢复停止并指出缺口（当前台账不受影响）；
6. 重启程序后备份与恢复记录仍在；「重置演示数据」可一键还原。

## 目录结构

```
app/
  core.py     # 台账核心：同事务写日志、链式校验、重放（幂等、调拨原子）
  backup.py   # 一致备份（在线备份接口 + 最后事务序号）
  restore.py  # 独立库重放、对照、确认切换、放弃、重启清理
  store.py    # meta.db：备份与恢复记录
  demo.py     # 种子数据、连续操作、故障注入、重置
  web.py      # Flask 页面与 API
  templates/  # 台账页、备份恢复页
run.py        # 启动入口
tests/        # 端到端逻辑测试
data/         # 运行时生成：live.db / meta.db / backups/ / staging/
```
